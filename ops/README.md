# การสำรองข้อมูลและกู้คืน PayBox

## สคริปต์

| ไฟล์ | ทำอะไร | ตารางเวลา |
|---|---|---|
| `backup.sh` | ดัมป์ฐานข้อมูล + ไฟล์ที่อัปโหลด | ทุกวัน 03:00 เวลาไทย |
| `restore-test.sh` | กู้ไฟล์ล่าสุดลง DB ชั่วคราวแล้วเทียบจำนวนแถว/ยอดเงิน | ทุกวันอาทิตย์ 03:30 เวลาไทย |

ติดตั้งอยู่ที่ `/opt/paybox/scripts/` บน VPS ไฟล์สำรองอยู่ที่ `/opt/paybox/backups/`

```
crontab -l                                    # ดูตารางเวลา
tail -20 /opt/paybox/backups/backup.log       # ดูผลล่าสุด
/opt/paybox/scripts/backup.sh                 # สั่งสำรองเดี๋ยวนี้
/opt/paybox/scripts/restore-test.sh           # ทดสอบกู้คืนเดี๋ยวนี้
```

## หลักที่สคริปต์ยึด

**ไม่ลบของเก่าจนกว่าของใหม่จะผ่านการตรวจ** — ดัมป์ต้องมีขนาดสมเหตุสมผล มีตารางสำคัญครบ
(`transactions`, `customers`, `devices`, `settlements`, `admins`) และมีบรรทัดปิดท้ายของ mysqldump
ถ้าข้อใดไม่ผ่านถือว่าล้มเหลวและไม่แตะไฟล์เดิม — backup ที่เสียแล้วไปลบของดีทิ้งแย่กว่าไม่มี backup
เพราะทำให้เข้าใจผิดว่าตัวเองปลอดภัย

**ใช้ `--single-transaction`** ได้ snapshot ที่สอดคล้องกันบน InnoDB โดยไม่ล็อกตาราง ระบบยังรับเงินได้ระหว่างดัมป์

**ข้ามโฟลเดอร์ `firmware`** ไฟล์ `.bin` สร้างใหม่จาก git ได้และกินที่มากสุด
ส่วน `settlement_proofs` (หลักฐานการโอนเงิน) สำรองเสมอ

**เก็บ 30 วัน** ปัจจุบัน DB ~8KB ต่อชุด และ uploads ~1.8MB ต่อชุด

## ⚠️ ข้อจำกัดที่ยังเหลืออยู่

**ไฟล์สำรองอยู่บนดิสก์ลูกเดียวกับฐานข้อมูล** ป้องกันได้แค่ข้อมูลเสียหาย migration พลาด หรือลบผิด
**แต่ถ้า VPS หายทั้งลูก ไฟล์สำรองก็หายไปด้วย**

ต้องดึงออกไปเก็บที่อื่นถึงจะเรียกว่าปลอดภัยจริง ตัวเลือก:

```bash
# ดึงลงเครื่องตัวเอง (รันจากเครื่องตัวเอง ตั้ง scheduled task รายวันได้)
scp root@$PAYBOX_HOST:/opt/paybox/backups/paybox-*-$(date +%Y%m%d)* ./backups/
```

ถ้าจะให้ VPS ส่งขึ้น cloud เองอัตโนมัติ ต้องมี credential ของผู้ให้บริการ (S3 / Backblaze B2 /
rclone ไป Google Drive) ใส่เพิ่มในสคริปต์ตรงท้ายก่อนขั้นตอนลบของเก่า

## กู้คืนจริงเมื่อเกิดเหตุ

```bash
cd /opt/paybox/platform
P=$(grep '^MYSQL_ROOT_PASSWORD=' .env | cut -d= -f2-)

# 1) หยุด backend ก่อน ไม่ให้มีใครเขียนทับระหว่างกู้
docker compose -f docker-compose.yml stop backend

# 2) กู้ฐานข้อมูล
gunzip -c /opt/paybox/backups/paybox-db-YYYYMMDD-HHMMSS.sql.gz \
  | docker exec -i paybox-mysql mysql -uroot -p"$P" paybox

# 3) กู้ไฟล์อัปโหลด
docker run --rm -v paybox-backend_paybox-uploads:/data \
  -v /opt/paybox/backups:/backup alpine:3 \
  tar xzf /backup/paybox-uploads-YYYYMMDD-HHMMSS.tar.gz -C /data

# 4) เปิดกลับ
docker compose -f docker-compose.yml start backend
```

# การกระทบยอดกับ Stripe

## Webhook

`POST /api/stripe/webhook` — Stripe ยิงมาบอกเมื่อสถานะการจ่ายเงินเปลี่ยน ตรวจลายเซ็น HMAC-SHA256
พร้อมกันการเล่นซ้ำ (ปฏิเสธ payload ที่เก่ากว่า 5 นาที)

ลายเซ็นอยู่ใน `.env` เป็น `STRIPE_WEBHOOK_SECRET` และส่งเข้า container ผ่าน `docker-compose.yml`
ถ้าค่านี้ว่าง endpoint จะตอบ 503 แต่ระบบยังบูตขึ้นได้ตามปกติ

**หมายเหตุ:** บัญชี Stripe นี้ใช้ร่วมกับโปรเจกต์อื่น (`<โฮสต์เดิม>/snoob`) ซึ่งมี webhook ของตัวเอง
อยู่แล้ว — อย่าลบของโปรเจกต์นั้น

## งานตามเก็บรายการค้าง

รันเองทุก 15 นาที ตามรายการที่ยังไม่จบและเก่ากว่า 10 นาที โดย **ถาม Stripe เสมอ**
ไม่ได้เดาว่าเก่าแล้วต้องหมดอายุ — บางรายการจ่ายสำเร็จจริงหลังบอร์ดเลิกถาม การปิดทื่อๆ
จะกลืนเงินของร้านค้าหายไปเงียบๆ

เลิกตามเมื่อ: เก่ากว่า 7 วัน หรืออยู่สถานะ `requires_payment_method` เกิน 24 ชั่วโมง
(PromptPay ที่ QR หมดอายุจะค้างสถานะนี้ถาวร ถ้าไม่กันไว้จะยิง Stripe เปล่าๆ วันละหลายพันครั้ง)

## การแจ้งเตือนเมื่อระบบมีปัญหา

`watch.sh` รันจาก cron ทุก 5 นาที ตรวจสามอย่างแล้วส่งข้อความออกทาง Telegram และ/หรือ LINE

| ตรวจอะไร | ถือว่าเสียเมื่อ |
|---|---|
| เว็บสาธารณะ | `https://orca-paybox.com/` ไม่ตอบ `{"ok":true}` ภายใน 15 วินาที |
| ฐานข้อมูล | `paybox-mysql` ไม่ตอบ `mysqladmin ping` |
| เครื่องรับเงิน | `is_active=1` และไม่มี heartbeat เกิน 10 นาที |

เฉพาะเครื่องที่แอดมินเปิดสวิตช์ไว้ **และเคยติดต่อเข้ามาแล้ว** เท่านั้นที่ถูกเฝ้า — เครื่องที่ยังไม่เคย
แฟลชหรือถูกปิดไว้ไม่ใช่ความผิดปกติ จึงไม่ควรส่งเสียง

### หลักการที่ยึด

- **แจ้งตอนสถานะเปลี่ยนเท่านั้น** ไม่ใช่ทุกรอบที่ยังเจอปัญหา การเตือนที่ดังทุก 5 นาทีจะถูกปิดเสียง
  ภายในวันเดียว แล้วหลังจากนั้นก็ไม่เหลือการเตือนอีกเลย ถ้ายังเสียอยู่จะย้ำอีกครั้งทุก 12 ชั่วโมง
- **รันบน host ไม่ใช่ในคอนเทนเนอร์** เพราะสิ่งที่ต้องเฝ้ารวมถึงตัว backend เอง ถ้าเอาตัวเฝ้าไปไว้
  ข้างในนั้น พอ container ตายตัวเฝ้าก็ตายไปด้วย
- **DB ล่ม = ข้ามการตรวจเครื่อง** ถ้าเดินต่อจะประกาศว่าเครื่องทุกตัวหายพร้อมกัน ทั้งที่ความจริงคือ
  เรามองไม่เห็นมันต่างหาก การเตือนที่ผิดทำลายความน่าเชื่อถือของการเตือนที่เหลือ

### ตั้งค่า credential

ตั้งจากหน้าเว็บ: **ตั้งค่า → การแจ้งเตือน** มีวิธีหา token ของแต่ละช่องอยู่ในปุ่ม "อ่านวิธีตั้งค่า"
พร้อมปุ่มทดสอบส่ง และปุ่มค้นหา `chat id` ของ Telegram ให้อัตโนมัติ

backend เขียนค่าลง `/opt/paybox/alerts/env.alerts` (chmod 600, เจ้าของคือ uid 100 ของคอนเทนเนอร์)
แล้ว `notify.sh` ที่รันเป็น root อ่านไฟล์เดียวกันนี้ — ทั้งสองฝั่งไม่ต้องรู้จักกัน และถ้า backend
ล่มทั้งตัว การแจ้งเตือนยังทำงานต่อด้วยค่าที่เขียนไว้ล่าสุด

ที่ **ไม่** เก็บใน MySQL เพราะหน้าที่หนึ่งของตัวเฝ้าระวังคือแจ้งว่า "ต่อฐานข้อมูลไม่ได้" —
ถ้าเอา credential ไปไว้ในฐานข้อมูล พอฐานข้อมูลล่มมันจะอ่านค่าไม่ได้แล้วเงียบสนิทพอดีกับตอนที่
ต้องส่งเสียงที่สุด

แก้ไฟล์ด้วยมือได้ แต่จะถูกทับเมื่อมีการบันทึกจากหน้าเว็บครั้งถัดไป
`telegram-chatid.sh` ยังใช้ได้อยู่เผื่อกรณีที่เข้าหน้าเว็บไม่ได้

LINE ใช้ **Messaging API** ไม่ใช่ LINE Notify — LINE Notify ปิดบริการไปแล้วเมื่อ 31 มี.ค. 2568
ตัวส่งจึงมีสองชุด (`ops/notify.sh` สำหรับ cron และ `src/lib/alertSend.ts` สำหรับปุ่มทดสอบใน
คอนเทนเนอร์) ถ้าแก้ปลายทางหรือรูปแบบข้อความ **ต้องแก้ทั้งสองที่**

### ตรวจว่ายังทำงานอยู่

```sh
cat /opt/paybox/state/last-run     # เวลาที่ตรวจรอบล่าสุด ควรห่างจากตอนนี้ไม่เกิน 5 นาที
cat /opt/paybox/state/*.state      # สถานะล่าสุดของแต่ละสิ่งที่เฝ้า
tail /opt/paybox/logs/watch.log    # log เฉพาะตอนมีเรื่อง ไม่ log รอบที่ผ่านปกติ
tail /opt/paybox/logs/alert.log    # ผลการส่งข้อความ
```

**ข้อจำกัดที่ต้องรู้:** ถ้า cron เองพัง หรือ VPS ดับทั้งเครื่อง จะไม่มีการแจ้งเตือนใดๆ ออกมาเลย และ
ความเงียบจะดูเหมือนทุกอย่างปกติ ปิดช่องนี้ได้ด้วยตัวเฝ้าที่อยู่นอกเครื่อง เช่น healthchecks.io ที่จะ
ส่งเสียงเมื่อ **ไม่ได้รับ** สัญญาณตามเวลาที่นัดไว้ — ยังไม่ได้ทำเพราะต้องมีบัญชีข้างนอก

## การปล่อยของขึ้น production

```sh
ssh root@$PAYBOX_HOST /opt/paybox/scripts/deploy.sh
```

ดึงทั้งสอง repo จาก bare repo บนเครื่อง แล้ว build image ใหม่และเช็คว่าเว็บกลับมา

### โครงบนเซิร์ฟเวอร์

```
/opt/paybox/
  git/paybox-platform.git  bare repo — ปลายทางของ git push
  git/paybox-legacy.git    PHP ชุดเดิม เก็บไว้อ่านอย่างเดียว
  platform/                clone (มี .env ที่ไม่อยู่ใน git)
  scripts/                 ตัวเรียกที่ cron ใช้
  alerts/ state/ logs/ backups/
```

`docker-compose.yml` ปักชื่อ project ไว้เป็น `paybox-backend` ตายตัว **ห้ามลบบรรทัดนั้น** —
ชื่อ project เป็น prefix ของชื่อ volume ถ้าปล่อยให้ compose เดาจากชื่อโฟลเดอร์ การย้ายโฟลเดอร์
จะทำให้มันสร้าง volume เปล่าใหม่เงียบๆ แล้วฐานข้อมูลจะดูเหมือนถูกล้างทิ้ง

เครื่องที่พัฒนามี `origin` ชี้มาที่ bare repo ผ่าน ssh การปล่อยของจึงเป็น

```sh
git push          # จากเครื่องตัวเอง
ssh root@$PAYBOX_HOST /opt/paybox/scripts/deploy.sh
```

### ทำไมต้องเป็นแบบนี้

เดิมปล่อยของด้วยการ `scp` ไฟล์ขึ้นไปทีละไฟล์ วันที่ 28 ส.ค. 2569 การ scp `docker-compose.yml`
ตัวที่เก่ากว่าขึ้นไปทับ ทำให้บรรทัด `STRIPE_WEBHOOK_SECRET` หายไปโดยไม่มีอะไรเตือน webhook ของ
Stripe ตอบ 503 อยู่ 37 นาที และไม่มีใครรู้จนกระทั่งไปเจอโดยบังเอิญ

git ไม่ได้ทำให้ความผิดพลาดแบบนั้นเกิดไม่ได้ แต่ทำให้มัน **มองเห็นได้** — `deploy.sh` จะหยุด
ทันทีถ้าเจอไฟล์ที่ถูกแก้ค้างไว้บนเซิร์ฟเวอร์ และแสดงว่าไฟล์ไหนบ้าง ต้องสั่ง `FORCE=1` ถึงจะยอมทับ

### เมื่อของใหม่มีปัญหา

`deploy.sh` ไม่ย้อน image ให้อัตโนมัติ เพราะการย้อนโค้ดโดยที่ยังไม่รู้สาเหตุอาจทำให้สถานะ
ฐานข้อมูลกับโค้ดไม่ตรงกัน ซึ่งแก้ยากกว่าปัญหาเดิม ให้ดู log แล้วตัดสินใจเอง

```sh
docker logs --tail 50 paybox-backend
git -C /opt/paybox/platform log --oneline -5
git -C /opt/paybox/platform reset --hard <commit ที่ใช้ได้>
/opt/paybox/scripts/deploy.sh
```
